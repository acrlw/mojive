# 与规格不一致的地方，以及还没裁决的问题

规格（`prompt/01～14`）写在另一台机器、另一个时间点上。实现过程中有若干处**照字面做会错**
或**本机做不到**。规格 §12.5 的纪律是"每一处差异只能落进两类，不允许含混"——
本文件是那张表在"实现 vs 规格"这一侧的对应物。

`docs/PLATFORM.md` 记的是**本机的 GL 事实**；`docs/RENDERER.md` 记的是**与参照渲染器的
差异**；这里记的是**与规格文本的差异**。

## 一、照字面做会错的（已改，并改了契约文档）

### 1. `as_strided` 那一段对 MuJoCo 的 Python 绑定不成立

规格 04 §4.3 / 13 §13.4 说"物理库的几何数组在 C 里是连续的结构体数组，同一字段构成一张
定步长表，用 `as_strided` 一次取完"。**MuJoCo 的绑定不是那种布局**：`geom_xpos` /
`geom_xmat` 各自是一整段连续内存，直接给出 `(G,3)` / `(G,9)` float64。所以正确做法更简单
也更安全——**整段一次拷贝进预分配缓冲**，不需要 `as_strided`，也就没有"越界读不报错、
读到的是垃圾"那个风险。

规格那段读起来像是唯一正确解法，实现时**要先看清自己面对的是哪种布局**。
开机仍做一次逐元素自检（拿一条独立取数路径比对），不过就退慢路径——那条纪律照留。

实测（Apple M5，本机）比规格的参照更悬殊：

| geom 数 | 整段一次拷贝 | 逐 geom 慢路径 | 倍数 |
|---|---|---|---|
| 401 | **0.9 µs** | 252 µs | 275× |
| 1501 | **2.8 µs** | 1145 µs | 404× |
| 5001 | **7.5 µs** | 3889 µs | 516× |

（规格给的参照是 401 geom 下 62 µs → 4 µs。本机的朴素路径比那个基线慢得多，
所以倍数也大得多。**两边的"慢路径"不是同一件事**，不要横向比这个倍数。）

### 2. `SceneNode.object_id`：只有 body 类节点带非零值

规格 04 §4.1 说"同一个 body 的多个 geom 必须用同一个 id"——那说的是 **ID buffer 里逐
geom 的 id**（`SceneSource.geom_object_id`）。但 `Session` 建的反查表是
`{object_id: node}`：**geom 节点若也带同一个 id，后来的会覆盖先来的**，反查落到最后一个
geom 上，`posable` / `set_pose` / 手柄全失灵，而且没有一处报错。

已在 `adapters/base.py` 的 `SceneNode.object_id` 上钉死：**只有 `ROBOT` / `LINK` 带非零
值，geom / joint / site 一律 0**，子节点用 `body_index` 指回去。

### 3. 拾取的第 2 级不是"不含静态几何"，而是"打中世界 body 当成没点中"

规格 07 §7.2 写"射线那条路走的是不含静态几何"。**照字面实现会让整份场景一个都点不中**：
MuJoCo 里"静态"指焊在世界上，而 `test_scene` / `pick_scene` 的每个地标 body 都是静态的。
而 ID buffer 会如实报出它们——**两条拾取路径当场分家**，正是这句话想避免的事。

让两边一致的规则是**"打中世界 body 当成没点中"**（地面确实属于世界 body，
选中它只会让手柄挂在原点）。另需按 geom 组过滤，否则会点中画都没画的碰撞体。

### 4. geom 自己的 `rgba` 只有被显式改过才压过材质

规格没写这一条，但它很咬人：MJCF 里 geom 的 `rgba` 出厂默认是 `0.5 0.5 0.5 1`。
无条件让 geom 覆盖材质的话，**贴了棋盘格材质的地板会被那份默认灰盖成一块死灰**——
画得出来，只是颜色全错。所以只有 `rgba` 被显式改过（≠ 出厂默认）时才覆盖。

### 5. 桶的身份要带"透不透明"

规格 04 §4.2 说桶键是 `(网格, 材质 id)`。但逐 geom 的 rgba 可以覆盖材质的 alpha，
于是同一个键下既可能有透明实例又可能有不透明实例，而它们**要进不同的 pass**。
内部的桶身份是 `(网格, 材质 id, 透不透明)`，对外仍按规格暴露二元组，两条 pass 靠
`opaque_buckets` / `transparent_buckets` 分。

### 6. `object_id` 是独立的 uint32 顶点属性

一度打算把它编进材质四元组的"预留"位（float32）。**那会重新引入 2²⁴ 上限**——
正是 07 §7.1 选 `R32UI` 要避开的东西（`mjr_` 的 `mjRND_IDCOLOR` 把 id 打包进 RGB8，
栽的就是这个）。现在它是一个真正的整数属性，上限 42 亿，"预留"位仍然留给将来的 metallic。

### 7. 后端自己持有场景构建器（协议必须是完整的契约）

一度让调用方建好 `RenderScene` 再通过 `set_render_scene()` 交给后端。**那是错的**：
`RenderBackend` 协议里没有那个入口，而 UI 层**不许 import 具体后端**（03 §3.9）——
于是主循环根本没有合法途径把场景喂进来。

现象：窗口开得出来、面板都在、物理在跑、`glGetError` 干净，**只有视口永远是空的**，
而 `render()` 只是老老实实返回 `None`（03 §3.5 说的就是它该这么做）。**哪一层都不报错。**

修法是把构建器放进后端：`set_scene(source)` 建它，`update(frame)` 用它。
构建器本来就是渲染侧的事（吃 `SceneSource`、吐 `RenderScene`，两头都与物理库无关）。

**教训**：一个"薄接口"如果**少了一环**，缺的那一环会在分层约束下变成死路。
判断接口完不完整的方法不是看它好不好看，而是问"**只用这个协议，调用方能把事办成吗**"。

### 8. `geom_rgba` 不是有效 alpha

geom 挂了材质而自己没写 `rgba` 时，`geom_rgba` 留着默认 `1 1 1 1`，**真正的 alpha 在
`mat_rgba` 里**。照 `geom_rgba` 判透明会得出 `transparency.xml`"一片半透都没有"——
而那份场景的全部意义就是透明。适配器写 `geom_rgba` 时要走与颜色同一条回退。

### 9. URDF 加载器默认 `discardvisual=true`

不在 `<robot>` 里塞 `<mujoco><compiler discardvisual="false"/></mujoco>` 的话，
`test_scene.urdf` 只剩地板一个 geom，**且不报错**。已写进那份资产的注释。

### 10. `parity_texture` 的"MJCF 内建程序化贴图 + 无对称四色格"自相矛盾

规格 11 要它"无对称的四色格"，又要求"不依赖外部图片文件"。实测 MJCF 的 builtin 只有
checker（2×2，**镜像 ≡ 半格平移**）/ gradient（是**径向**的，不是线性渐变）/ flat 三种，
`mark` 只有 edge/cross/random——**做不出一张无对称的四色贴图**。

处理：四色格拼在**几何**上（16 块共面砖 × 4 色，排布经 8 个二面体操作 × 16 平移 ×
24 换色全部校验过无对称），每块砖再贴灰阶 checker 保住贴图路径；另加一块
`mark="random"` 板作为唯一真正无对称的程序化贴图。

### 11. `many_objects` 是 17 次绘制，不是规格参照的 6 次

规格 04 §4.2 的参照是"401 geom / 6 次绘制"。这份场景**故意**用 4 材质 × 4 形状
（16 种组合各 25 次 + 地板 = 17 个桶），因为它要看门的正是"**尺寸不进桶键**"——
只有一种材质的话，那条性质根本触发不到。

值得记的一次假绿：第一版材质规律取 `(3x + 5y) mod 4`，那个矩阵行列式是 2、mod 4 不可逆，
**实际只出现 8 种组合**，桶数悄悄少一半而画面毫无异样。

### 12. 叠加层在 `SHARED` 布局下会污染 ID buffer

规格 08 完全没提 ID buffer。但在 `SHARED` 布局下主 FBO 挂着第二个 `R32UI` 附件，
而 debug draw / 描边这些叠加层的片元着色器**只写 0 号输出**——1 号附件拿到的是未定义值。
后果：标注**底下**的像素拾取到垃圾 id。

已用 `color_mask` 把 1 号附件屏蔽掉。本机是 `SPLIT`、走不到这条，**但别的机器会**——
这类"只在另一台机器上出现、且不报错"的缺陷正是本文件存在的理由。

### 13. `sector` 的半径：规格自相矛盾

08 §8.3 把扇形半径列在**屏幕域**（存像素值），而 §8.5 的 `sector()` 签名里**没有半径
参数**。调和：默认用参考向量自己的世界长度，另给一个**只能按关键字传**的 `radius_px`
走屏幕域，位置参数逐字不变。

同理 `frame()` 没有线宽参数，而轴长是实体域、线宽必须是屏幕域——只能给一个模块常量。

### 14. 扰动反馈两档都走 `ALWAYS`（用户要求，偏离 08 §8.2）

08 §8.2 给**平移**建议 `GHOST`：被挡的部分用低不透明度画出来，理由是"目标点在那面墙
前面还是后面"是真要回答的问题。用户明确要求这套反馈**一律画在最前面、不被场景遮挡**。

裁决：**照用户的**。正在拖的时候"我拖到哪了"比"它在墙的哪一侧"更要紧，后者松手看物体
本身就知道；而拖拽反馈被墙吃掉半截，人会以为是控件坏了。
`ui.perturb.drag` 与 `ui.perturb.mark` 因此都是 `ALWAYS`。
判据：`tests/test_perturb.py::test_layers_and_occlusion_tiers_match_the_spec`。

### 15. XYZ 三色**保持配平过的那一套**（原生 gizmo 已统一）

问题是真的：**同一根 X 轴出现了两个红**——视口坐标架、视角轴球、扰动标注用 THEME
那一套（`#ef6e6a` / `#54a853` / `#6993f6`），物体手柄用 ImGuizmo 自己的
（`0.666,0,0` 等，纯三原色）。用户提出统一色盘。

**只能单向统一**：ImGuizmo 的 `Style::Colors[]` 在 Python 绑定里既读不到也写不了
（`get_style()` 只暴露线宽与尺寸），所以要么 THEME 迁就它，要么不统一。

**试过迁就，开起来看之后退回。** 代价太大：THEME 那一套在 CIE L\*C\*h 下同
L\*=62、同 C\*=56，三根轴在灰度上一样重；纯三原色的 L\* 是 53 / 88 / 32，
深色背景上蓝轴压不住、绿轴又跳出来，整幅画面一根比一根"重"。
而**手柄只是屏幕上一小块控件，轴色却铺在整个视口、坐标架、轴球和扰动标注上**——
让多数迁就少数划不来。

后来物体手柄换成 forge 原生 3D pass，不再受 ImGuizmo 样式接口限制。裁决更新为：
**保持配平的那一套，并让原生手柄也使用同一组 RGB。**
判据 `test_axis_colors_are_luminance_balanced` 钉住配平，`test_native_gizmo_uses_theme_axis_colors`
钉住两处不再漂开。

### 16. 平面反射不用 stencil，改用"离屏反射图"（偏离 14 §M5.2 的措辞）

规格写的是"镜像 pass + **stencil 限制在平面轮廓内** + winding 翻转 + 斜裁剪面"。
四件事里后两件照做，**stencil 那件换成了"渲进一张离屏图、反射面在自己的着色里按屏幕
坐标采它"**。两条理由：

1. **本机拿不到 stencil。** moderngl 5.12 的 `Context.enable()` 只有
   `BLEND / CULL_FACE / DEPTH_TEST` 等几位，**没有 `STENCIL_TEST`**；
   `framebuffer()` 的深度附件走 `depth_texture` / `depth_renderbuffer`，
   都建不出 DEPTH24_STENCIL8。要用它就得整条自己走 ctypes（附件、`glStencilFunc`、
   `glStencilOp` 全套）。
2. **"限制在平面轮廓内"在这条路上是自动的。** 只有 `reflectance > 0` 的片元才去采
   反射图，而那正好就是反射面自己的片元；遮挡仍由主 pass 的深度测试管
   （反射面是照常画的，不是先清深度再补画）。

代价一样：都要把不透明几何再渲一遍。多出来的是一张全屏 RGB16F。
判据 `tests/gpu/test_reflection.py` 判的是**结果**（倒影在不在、只在地板上、
加法律、地板底下的东西不漏、看到的是外壁），与用哪种机制无关。

## 二、本机做不到的

见 [`PLATFORM.md`](PLATFORM.md)：整数附件进不了 MSAA FBO（ID buffer 走独立目标 + 一趟
廉价 pass）、`glLineWidth` 上限 1、KHR_debug 缺失、逐 pass GPU 计时在 TBDR 上不可分摊。

**`mujoco-classic` 这条后端**（在同一个进程里用 `mjr_` 当渲染后端）在 macOS 上确实起不来：
它要 compat profile，而 forge 要 core，同进程互斥。**但那不影响 `make parity`**——
对拍本来就把参照渲染器放在**子进程**里（规格 §12.5 的原话），子进程建自己的 legacy
上下文，`mujoco.Renderer` 离屏出图一切正常。**这两件事一度被我混为一谈**，
详见下一节开头的更正。

## 三、已经裁决的（`make parity` / `make calibrate` 跑通之后）

> **更正**：这一节曾经写着"本机跑不了对拍，所以定不了"。**那是错的。**
> `mjr_` 要的是 legacy 上下文，macOS 提供得了（GL 1.5 固定管线是 GL 2.1 的子集），
> `mujoco.Renderer` 离屏出图实测正常。不能共存的是**上下文**，不是**机器**——
> 而规格 §12.5 早就写了参照渲染器跑在**子进程**里。
> 把"不能同进程共存"读成"这台机器上跑不了"，白白搁置了整个对拍关卡。

### 1. `LightSet.ambient` 的来源 —— **已裁决：两处相加**

拿参照渲染器实测（`make calibrate`，纯色板 rgba=0.95）：

| 配置 | 参照 | 旧实现 | 现实现 |
|---|---|---|---|
| 只有 `headlight.ambient=0.4` | 97 | 97 | 97 |
| 只有 `light.ambient=0.4` | **97** | **0** ✗ | 97 |
| 两处都是 0.4 | **194** | 97 ✗ | 193 |
| 两处都是 0 | 0 | 0 | 0 |

旧实现是"头灯开着就只用头灯，否则取各灯的逐通道最大值"——**逐灯 ambient 整个被丢掉**。
现在改成**相加**（逐灯只累加 active 的那些）。

同一趟还推翻了 §5.2 的 ×2：参照只算一遍。见 `docs/RENDERER.md` 的"已推翻"一节。

### 2. 无限平面跟不跟相机走

规格 05 §5.5 说参照渲染器的平面是跟着相机走的（吸附到 2 个贴图周期）。现在的实现是
"半边长 = 相机水平偏移 + 远裁剪面，吸附到整周期"，**平面仍钉在 geom 原点**。
好处是相位在世界里严格不动；代价是对拍时平面边缘位置与参照不同。要看对拍图裁决。

### 3. 贴图面要不要着色 —— **已裁决：着色，forge 本来就对**

规格 12 §12.5 说参照"对贴图面完全不着色（环境光 0.5 与 1.0 两档输出相同）"。
**MuJoCo 3.11.0 上不成立**——实测纯色贴图面（texel 0.6）：

| ambient | 参照 | forge | `a × texel × 255` |
|---|---|---|---|
| 0.25 | 38 | 39 | 38.2 |
| 0.50 | 77 | 75 | 76.5 |
| 1.00 | 153 | 151 | 153.0 |

**线性缩放**，贴图面确实受光。forge 一直是着色的，不用改。

### 4. `arrow` 有两种表示，要选一种

08 §8.1 把 `arrow` 列为 **2 顶点的线图元**；而 `MeshShape` 里又有 `ARROW_SHAFT` /
`ARROW_HEAD` 两份**实体网格**。两处对"箭头"的表示不一致。
debug draw 走线图元那条（屏幕恒定宽度、三角形带展开）；实体网格留给需要透视缩放的场合。
**不要让同一个 `layer.arrow()` 有时走这条有时走那条**——那会让同一份脚本在不同场景里
画出粗细语义不同的箭头。

### 5. `tex_coef` 表达不了 `texuniform` 的完整语义

逐实例只有一组 (u, v) 缩放，而一个非立方体盒子的六个面用的是三对不同的轴——精确做法要
在着色器里做物体空间 texgen。标定用的 1×1 m 立方体恰好掩盖了这一点。现按
(extent_x, extent_y) 实现。**非立方体盒子的贴图密度在某些面上是错的**，
要不要修取决于有没有场景真的需要。

## 四、规格里那几条"判据"本身是假绿的

实现过程中逐条反向验证时发现的（12 §12.1 的同一类问题，只是出现在规格给的判据上）：

| 规格给的判据 | 为什么是假绿 | 换成什么 |
|---|---|---|
| 09 §9.3「俯仰 > 80° 时按 `q`，`eye.z` 仍然增加」 | 沿视线上方的错误实现在 85° 时 `up.z ≈ 0.087 > 0`，`eye.z` 照样增加——**全绿**，而水平位移是抬升量的 11 倍 | 判「抬升量是命令的**全量**且水平位移恒为 0」 |
| 12 §12.1 例 1「翻转环的法线，物体转向必须不变」 | 现行第 5 版扰动反馈**没有环、没有选中轴**，也就没有法线可翻；而轴符号与标量符号一起翻是**同一个旋转**，那不是缺陷 | 判「只翻一根轴时，投影到屏幕上的转向要变」——实测复现了原例想抓的那个假绿 |
| 09 §9.2「同一帧相机与扰动不会同时活动」 | 归属是枚举，天然互斥——**自证** | 判「归属在按下那一帧锁定」，且要挑扰动被 `Reset` 清掉的那一帧，否则仍是假绿 |
| 03 §3.7「0.3 秒内的连续变化只触发一次重建」 | 对任何 ≥ 0.05 秒的迟滞都成立，守不住 0.6 这个数 | 判「一次人手停顿（0.25 秒）不该触发重建」——那才是规格给 0.6 的理由 |

## 五、量出来但没有改的

- **级联矩阵计算 0.052 ms CPU**（规格 06 §6.7 已记）。批量化能收掉，但那是带纹素吸附的
  矩阵数学，**改动风险高于收益**。记下来，不要为它冒险。
- **本机驱动分辨不出 `glVertexAttribPointer` / `IPointer`**（按位重解释）。代码仍走规范
  要求的那个，但**画面判据在这台机器上守不住它**，只能守住声明的类型。见 PLATFORM.md §3。
