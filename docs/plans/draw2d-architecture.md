# 自研 Draw2D 架构与 CLI/RPC 补齐方案

状态：设计提案。现状依据为 2026-09-12 检查的代码，已提交基线见配套实施清单。
本文描述的自研渲染器和控制接口改动尚未实现。此前的 Scale 和 UI 缓存优化已经提交，
但不代表 CLI/RPC 功能缺口和核心代码清理已全部完成。

实施交接入口：[需求、任务清单、源码导航与验收步骤](draw2d-implementation.md)。
接手 agent 先读该清单中的第 0 节，再按任务依赖执行；本文负责说明架构决策。

## 方案概览

建立 Mojive 自己的矢量绘制与合成模块，负责路径处理、描边、抗锯齿、裁剪、透明度和 GPU 提交。
Python 保留为公共接口；C++ 负责几何编译、紧凑数据记录和批量处理；GPU 工作复用现有渲染后端与运行时。

核心原则是：**图形资源可以长期复用，每帧只提交实例的变换、颜色和裁剪等变化。**
独立绘图必须能够在不导入 ImGui、不创建 ImGui 上下文、不创建 ImDrawList 的情况下渲染到离屏目标。

迁移期继续使用 ImGui 管理原生控件、停靠、焦点、键盘导航和文本编辑。它作为合成器的一个输入来源，
与自研绘图按正确顺序组合。Mojive 自定义图形的路径和三角形缓冲不再经过 ImGui。
全面替换控件布局与编辑系统属于另一项工作，不是自研绘图的前置条件。

首版采用“简单图形解析绘制 + 复杂路径缓存网格”的组合。通用计算着色器光栅化、完整文本引擎重写、
为所有图标生成固定分辨率位图，均不作为起步方案。

## 一、现有实现与确定的缺口

| 范围 | 已确认的代码事实 | 对方案的影响 |
| --- | --- | --- |
| 绘图抽象 | `ui/draw2d.py` 已定义后端中立的 `Draw2D` 协议。 | 保留调用方式，将正式契约移出 `ui`，旧导入路径提供兼容入口。 |
| 几何依赖 | `_concave_indices` 创建临时 ImGui draw list；`ImguiDraw2D` 负责描边、填充提交和抗锯齿。 | 当前只有抽象接口，还没有独立的几何编译器与渲染器。 |
| 原生合成 | `Render.hpp` 中的 `UiVertex`、`UiCommand`、`UiFrame` 不含 ImGui 类型。 | 可以扩展现有合成契约，复用设备、目标、纹理和运行时的所有权。 |
| 上传链路 | `NativeWindow._draw_packet` 将 ImGui 数据复制到 NumPy，绑定层再复制到原生数组，bgfx 最后上传临时缓冲。 | Python 几何缓存没有消除逐帧提交开销。这些复制已由代码确认，但尚未分别测量其耗时。 |
| 后端一致性 | OpenGL、WebGPU 的窗口合成仍调用各自的 ImGui 渲染器。 | 只实现 bgfx 路径，不能替换默认 OpenGL 的 UI 绘图。 |
| Scale RPC | 已有 `commands.SetScale`，但 `operations.py` 没有 `set_scale`。 | 已安装 CLI 的操作查询返回 `unknown_method`，CLI/RPC 尚不能使用该操作。 |
| 对象查询 | `_node_payload` 和查询 schema 没有 `scalable` 及 Scale 语义。 | 远程调用方不能可靠获知某个对象是否可缩放；仅有适配器级能力不够。 |
| RPC 调度 | `ViewerControlService` 使用无界队列，每帧最多处理 64 条，没有耗时预算。 | 请求突发会积压并占用 UI 帧时间；数量限制不能约束单个昂贵操作。 |
| RPC 消息与连接 | socket 处理使用无长度限制的 `readline()`，每个连接创建一个线程。 | 需要消息长度、连接数量限制，以及明确的过载响应。 |
| 编辑批处理 | RPC `edit_scene` 使用历史事务；UI Apply 还会进入 `adapter.model_edit_batch()`。 | 合并 Undo 与延迟后端计算是两回事。RPC 尺寸编辑可能重复执行 `mj_setConst`/`mj_forward`，不能据此说每次都重新编译模型。 |
| UI 顺序衔接 | 原生数据提取跳过零元素命令，没有转换 ImGui 回调。 | 必须实现专门的插入标记桥接；把所有自定义图形最后再画，会破坏遮挡顺序。 |

现有控制层已经具备操作发现、JSON schema、文档前置条件、事务、截止时间、异步截图和共享内存截图。
补齐工作应扩展这些现有模块，避免再建一套命令注册、序列化或 RPC 执行系统。

## 二、模块划分与职责

```text
面板 / 视口控件 / 图标 / 离屏绘图工具
                    │
          mojive.draw2d 公共接口
      路径 / 可复用图形 / 帧记录 / 样式
                    │
          CPU 几何编译与有序帧记录
          几何资源 + 实例 + 裁剪
                    │
     合成器：自定义绘图 + ImGui 导入内容
                    │
       OpenGL / WebGPU / bgfx 执行器
                    │
          现有窗口、目标与运行时
```

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| `mojive.draw2d` | 公共类型、路径、绘图记录、兼容入口 | Session、物理、原生设备句柄、当前 ImGui 窗口 |
| 共享几何编译器 | 曲线离散化、描边展开、填充拓扑、几何边界 | 主题颜色、选择状态、窗口生命周期 |
| 帧记录器 | 有序实例、变换、颜色槽位、裁剪与组边界 | 仿真命令、隐式全局 UI 状态 |
| UI 合成器 | 外部 UI 与自定义绘图的准确穿插顺序 | 图标形状、控件业务逻辑 |
| 后端执行器 | 上传、着色器、目标切换、同步、资源回收 | 每个控件自己的绘图公式 |
| UI 适配层 | 布局定位、输入归属、迁移期的 ImGui 插入标记 | 自定义剖分、直接调用 GPU |
| 现有调试绘图 | 持久化诊断 ID、有效期、预算、世界坐标和深度语义 | UI 焦点、停靠、文档编辑 |

复用 `curves2d`、`draglink2d`、图标定义和现有调试网格契约。将测量确认的 CPU 热点迁入同一套原生实现，
保留 Python 参考几何用于正确性比较，避免三个后端各维护一套剖分算法。
现有公共 `Canvas2D` 使用世界坐标，因此新的逻辑 UI 绘图接口不复用这个名称。

## 三、术语与接口命名

接口名应说明操作语义。以下术语分别描述不同层次，不能互相替代：

| 术语 | 含义 | 本方案中的用法 |
| --- | --- | --- |
| 批处理（batching） | 收集有序绘制项，再按兼容状态组织提交。 | 公共批量入口使用 `draw_batch`；仍然允许拆成多个渲染批次。 |
| 渲染批次（render batch） | 编译器根据管线、纹理、裁剪和图层等状态形成的提交单元。 | 属于后端组织方式，不要求业务代码手工划分。 |
| 实例化（instancing） | 多个对象复用同一份几何，使用各自的变换、颜色等实例数据。 | 公共入口使用 `draw_instances`，表达同一图形的多个实例。 |
| 实例化绘制（instanced draw） | GPU 绘制调用中的实例化执行机制。 | 后端映射到图形 API 的实际实例化命令，不与公共批量入口混为一谈。 |
| 多重绘制（multi-draw） | 用图形 API 的一个入口记录或执行多个 draw。 | 作为后端可选优化，不作为所有批量调用的承诺。 |

这些术语有明确的行业用例：MonoGame 使用 [SpriteBatch](https://docs.monogame.net/api/Microsoft.Xna.Framework.Graphics.SpriteBatch.html)
组织精灵和文字的绘制批次；Direct3D 使用 [DrawInstanced](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-drawinstanced)
表达复用几何的实例化绘制；Vulkan 的 [vkCmdDrawMultiEXT](https://docs.vulkan.org/refpages/latest/refpages/source/vkCmdDrawMultiEXT.html)
记录一组中间没有状态变更的有序 draw。

本方案不采用仅表达“绘制多个”的模糊命名。`draw_batch` 和 `draw_instances` 是 Mojive 按语义选择的公共名称，
并不是声称行业存在统一的函数拼写标准。它们均不保证只产生一次 GPU draw call。

## 四、公共接口契约

以下名称和签名属于拟议接口，目前尚不能直接调用。

| 类型 | 契约 |
| --- | --- |
| `Path2D` | 不可变路径操作与控制点；支持移动、直线、二次曲线、三次曲线、圆弧、闭合；明确使用 `nonzero` 或 `evenodd` 填充规则。 |
| `StrokeStyle` | 描边宽度、端帽、连接方式、尖角限制、宽度所属坐标空间。G3 轮廓是几何定义，不是抗锯齿开关。 |
| `Paint` / `PaintSlot` | 首版支持纯色 RGBA；命名槽位允许逐帧绑定主题或 hover 颜色，不触发路径重编译。 |
| `Drawing2D` | 局部坐标中的不可变、可复用几何与绘制命令。持有逻辑资源引用，不持有设备指针。 |
| `Frame2D` | 仅在当前帧有效的记录器；记录图形实例、路径、图像、排版后的文字，以及显式变换、裁剪和图层。 |
| `FramePacket2D` | 冻结的有序命令及资源租约；在消费完成之前拥有或保留全部引用数据。 |
| `Draw2DStats` | 分别统计编译、记录、上传、提交、GPU、缓存、内存和超限情况。 |

### 4.1 常规绘制

图标定义或调节参数发生变化时，准备一次图形资源。每帧只更新实例参数：

```python
builder = DrawingBuilder2D()
builder.fill_path(rotate_outline, paint=PaintSlot("foreground"))
rotate = builder.finish()

frame = recorder.begin_frame(logical_size=(width, height), framebuffer_scale=dpi)
with frame.clip_rect(panel_bounds):
    frame.draw(
        rotate,
        transform=Affine2D.translation(x, y) @ Affine2D.scale(icon_scale),
        paints={"foreground": theme.primary if selected else theme.text},
        opacity=disabled_opacity,
    )
packet = frame.finish()
runtime.render_2d(packet, target=surface)
```

保留 `line`、`rect`、`circle`、`arrow`、`polyline` 等便捷方法，并为既有 `Draw2D` 签名提供适配。
高级入口为 `fill_path`、`stroke_path` 和 `draw_mesh`；业务接口不暴露某一种抗锯齿实现的细节。

### 4.2 批量提交与实例绘制

| 拟议接口 | 输入语义 | 顺序与实现约束 |
| --- | --- | --- |
| `frame.draw_batch(items)` | 一组有序绘制项，可包含不同图形及其参数。 | 保留输入绘制顺序；只合并兼容的相邻项，不为减少批次破坏透明合成。 |
| `frame.draw_instances(drawing, transforms=..., paints=...)` | 同一 `Drawing2D`，配套连续的变换与颜色槽位数组。 | 实例数量与数组长度必须一致；根据图形的内部操作和图层语义生成一个或多个批次。 |

例如大量相同图标可以共享一份图形资源：

```python
frame.draw_instances(
    rotate,
    transforms=icon_transforms,
    paints={"foreground": icon_colors},
)
```

对于内部含有多次绘制或透明组的 `Drawing2D`，实例展开必须保持逐实例的视觉顺序；不能简单地先画所有实例的
第一个部件、再画所有实例的第二个部件。能否采用一次 GPU 实例化提交，由编译器在语义允许时决定。

普通调用已经由帧记录器自动组织批次，不要求所有控件改写成手工 batch。数组入口用于降低大量元素的
Python 调用和对象分配成本，不要求每个顶点创建 Python 对象或单独跨越 Python/C++ 边界。

### 4.3 边界与定位

区分 `geometry_bounds`、`stroke_bounds` 和 `layout_bounds`：几何边界、包含描边的边界、布局占位边界。
橙色参考圆属于诊断辅助线，不是裁剪蒙版。剔除与离屏分配使用变换后的描边边界，并为抗锯齿留出外扩范围。

命中测试可以复用几何，但点击容差仍由交互层决定。图形资源不内置自动居中或光学偏移；
已确认的图标布局规则负责定位，预览与正式 UI 使用同一个定位结果。

## 五、几何、抗锯齿与透明合成

### 5.1 坐标与线宽

统一使用逻辑 UI 坐标：原点在左上，X 向右，Y 向下。帧描述负责逻辑坐标到物理像素的转换，UI 缩放只应用一次。
抗锯齿覆盖率以物理像素计算。

屏幕空间描边保持固定物理像素宽度；局部空间描边随图形变换。非均匀缩放应作用于整个描边轮廓，
不能随意选一个缩放系数作为线宽。奇异变换必须有明确的空图形或退化结果语义。

### 5.2 绘制路径

圆、圆环、简单圆角矩形和胶囊线段，在覆盖率能够明确定义时，使用实例化四边形和解析覆盖率。
G3 轮廓、箭头、组合图标和任意路径使用缓存索引网格。

通用路径需要处理孔洞、绕向、退化和自交，不能用“从中心连三角形”代替通用剖分器。
独立的剖分组件可以经过依赖审查后引入，封装在 Mojive 契约内部。脱离 ImGui 不等于每个数值算法都必须从零发明。

按投影后的误差自适应离散曲线。可以从 0.25 物理像素的误差阈值开始评估，再与参考图验证；
这是拟定的质量起点，不是已验证的性能指标。局部网格按路径版本、描边参数和投影缩放级别缓存，
平移和颜色不进入几何缓存键。放大后的帧发布前，必须获得足够精度的几何。
屏幕空间描边的缓存还需要包含其语义要求的相关变换信息。

### 5.3 覆盖率

覆盖率属于完整填充区域。内部三角形边不能附加抗锯齿边缘。细路径、自重叠、描边连接处相交和孔洞，
需要依据拓扑处理覆盖率，或走明确的蒙版路径；给各个三角形独立加透明边缘不足以保证正确性。

解析距离覆盖率是快速路径，不是适用于所有图形的精确光栅化方法。
多重采样或蒙版的补充路径必须在三个后端保持相同的填充语义。

### 5.4 组合图标的透明度

**一个 draw call 不代表一个整体合成图形。** 即使共用顶点和索引缓冲，重叠部件仍可能逐个参与混合。
接口必须区分：

- 单次绘制的颜色透明度：部件之间的叠色是预期结果。
- 同色图形的几何并集：先形成合并区域，再应用一次颜色。
- 整个图形或组的透明度：先在透明黑背景上完成组内绘制，再将结果整体合成一次。

单色图标可以采用不重叠的合并区域，或并集覆盖率蒙版，避免分配临时彩色目标。
多色图形的整体透明度使用按实际边界分配、可复用的离屏图层。
嵌套图层保留各自的透明度，不能把父级透明度逐项乘到每个子部件上。
对独立的部分覆盖率简单取 `max`，也不普遍等价于采样层面的几何并集。

合成颜色使用预乘 alpha：覆盖率和透明度同时作用于 RGB 与 alpha；source-over 为
`source + destination * (1 - source_alpha)`。
组隔离与合成语义依据 [W3C 合成模型](https://www.w3.org/TR/compositing-1/#isolatedgroups)：
组内初始背景为透明黑，只有最终合成时才与父级背景交互。

### 5.5 色彩与小尺寸显示

颜色、图像和目标都必须声明颜色编码与 alpha 编码。预乘 alpha 本身并没有定义是否在线性光空间中混合。
ImGui 导入内容在边界完成规范化，分别验证现有显示编码的兼容效果和线性目标。
混合空间变化可能改变细线的视觉粗细，可参考 [Skia 的光栅化说明](https://skia.org/docs/dev/design/raster_tragedy/)。
迁移过程中不能悄悄改变已经确认的配色。

Rotate 的 stroke 和 gap 始终属于同一局部坐标系的几何尺寸。
小于一个像素的间隙不能保证在所有尺寸下都表现为完整的空白像素；应与按比例缩放的参考覆盖率比较，
而不是增加隐含的最小间隙或自动光学偏移。

## 六、性能与资源生命周期

1. **复用几何与上传结果。** 不可变路径和网格编译一次，在对应设备代次中上传一次。
   主题变化更新颜色，移动更新变换，滚动更新裁剪和位置。
2. **预热与任务合并。** 预热可见图标组和着色器变体。CPU 工作线程编译不可变几何，渲染所有者创建和回收 GPU 资源。
   滑块连续变化按版本合并过期任务，避免把每一个中间值都排入队列。
3. **连续数据与缓冲复用。** 复用帧内存区和实例数组，批量跨越语言边界。
   异步生命周期需要独立数据时保留必要的复制，不能一边复用可变 Python 缓冲，一边宣称零复制。
4. **复用现有渲染运行时。** 沿用有界的在途帧机制，帧数据保留资源租约，缓冲复用等待对应的完成栅栏。
   不在 `RenderRuntime` 上再叠加一条无界绘图线程或队列。
5. **按顺序合并批次。** 只合并管线、纹理、裁剪和图层状态兼容的相邻操作。
   保持绘制顺序，不能把所有透明图形按材质重排。bgfx UI view 继续使用顺序模式；其内部
   [提交与排序模型](https://bkaradzic.github.io/bgfx/internals.html)仍由 Mojive 现有运行时统一管理。
6. **提前剔除和内存预算。** 在昂贵编译前进行低成本边界剔除。
   几何、纹理、图层池同时限制字节数和条目数；尚未消费的帧所引用的资源不能被回收。
7. **后端选择上传策略。** 使用可复用或环形缓冲，并跟踪完成状态；仅在支持时使用持久映射。
   容量按块管理，公共接口不要求某个特定 OpenGL 扩展。
8. **超限行为明确。** 超大帧返回明确的预算错误，或使用有界、保序的分块提交。
   不允许静默漏画图标、复用失效句柄或无限创建离屏图层。

最初可以把独立编译的几何提交给扩展后的中立 UI 数据包，随后再通过常驻几何资源和实例化消除重复上传。
不另外建立第二套图形设备抽象，也不把所有形状实现继续塞进一个 bgfx 专用的大类。

## 七、文本与安装边界

文本由独立的 `TextLayout` 和字体服务管理，共享文字塑形、度量、字体回退和字形图集。
迁移初期，原生文本编辑仍由 ImGui 负责。临时字体图集导入器必须隔离，独立绘图需要自己的字体提供者。
引入 FreeType、HarfBuzz 或其他文字处理组件，需要核对打包与许可证。
图像四边形接口不能代替 Unicode 塑形、基线对齐、输入法和无障碍行为。

当前包支持纯 Python 安装及可选原生扩展。新编译器先作为明确可查询的能力，提供不依赖 ImGui 的纯 CPU 构建，
供 OpenGL、WebGPU、bgfx 共同使用。旧渲染路径是显式的迁移选项。
仅导入 Draw2D 不应隐式要求创建 bgfx 设备。

切换默认实现之前，需要明确安装兼容策略并准备平台 wheel；自研渲染器不可用时，不能悄悄回退到 ImGui，
同时对外声称已经独立。

## 八、与 ImGui 的过渡合成

合成数据包包含外部 UI 绘制段和自定义绘制段。桥接层在自定义控件实际所在的 ImGui 绘制通道中插入带类型的标记。
通道合并和窗口排序完成后，导入器将标记替换为对应的自定义绘制段。
裁剪状态、窗口顺序、弹窗与模态层级、资源引用都必须完整保留。

当前原生导入器尚不支持这种标记，需要实现并测试。标记负载复制保存，使用稳定的帧内 ID；
不能让 GPU 线程执行 Python 回调，也不能引用已经失效的临时对象。
已识别的渲染状态重置标记需要显式处理，其他外部回调不能被静默丢弃。

将离屏纹理作为普通图像插入，可用于范围受控的过渡阶段，但会增加分配、填充和过滤成本，
不是最终通用方案。

独立目标完全绕过 ImGui 导入器；三个后端执行同一套有序的自定义绘图数据。
需要场景深度测试的调试绘图继续保留原有 render pass 与遮挡契约，同时共享适合复用的形状资源和算法。

## 九、CLI/RPC 补齐顺序

| 优先级 | 工作 | 必须满足的行为 |
| --- | --- | --- |
| 第一阶段 | 在 `operations.py` 增加 `set_scale` | 正数 XYZ 因子、能力与目标检查、文档前置条件、事务支持、尺寸只烘焙一次、随后恢复 identity。该操作具有乘法语义，不能自动重试。 |
| 第一阶段 | 扩展对象查询 schema 和结果 | 返回对象级缩放能力及明确的生效值、待应用值语义，区分已提交的文档状态与本地未提交预览。 |
| 第一阶段 | 审计命令覆盖范围 | 将相关命令归类为公共操作、内部事务或本地交互；明确未公开的原因，不自动把所有 UI 命令暴露为 RPC。 |
| 第一阶段 | 共享批处理执行策略 | 为 UI Apply 与 RPC `edit_scene` 提取统一的已校验编辑计划，保留顺序、真实对象身份、失败回滚证据、单条历史记录和适当的后端批处理。不能直接嵌套现有事务函数。 |
| 第二阶段 | 限制请求工作量 | 队列容量、消息字节数、连接数量、每帧数量与耗时双重预算，以及明确的 `busy` 和超限错误。 |
| 第二阶段 | 将昂贵准备工作移出 UI 线程 | 复用现有任务所有者，在所属线程原子发布结果。帧预算不能抢占已经开始的阻塞操作。 |
| 第二阶段 | 暴露渲染诊断 | 通过现有操作目录增加有类型的只读绘图统计，复用已有截图链路，不另建开发专用 socket 协议。 |
| 后续 | 事件与任务查询 | 用有界、基于版本的变更通知和任务状态降低轮询；保留截止时间及 `completion_unknown` 语义，没有明确去重契约时不承诺恰好执行一次。 |

连接到 Viewer 的 RPC 当前有意绕过 UI 草稿拦截器。草稿冲突策略应统一放在应用边界：
用户存在未提交草稿时，文档修改应明确失败，或通过明确的草稿操作处理，不能误把预览尺寸当作已提交的文档状态。

CLI 继续作为 schema 驱动的客户端，不重新实现编辑校验、居中规则、Scale 数学或重建策略。

## 十、实施阶段与验收

1. 补齐 Scale 操作及查询，在无窗口和连接 Viewer 两种方式下验证行为一致。
   替换绘图提交之前，记录冷启动、缓存命中和原生上传开销的基线。
2. 实现纯 CPU 契约、几何编译器和自研离屏渲染器。
   在不导入 ImGui 的情况下验证填充规则、孔洞、变换、裁剪、组透明度与失败路径。
3. 实现合成器穿插和所有支持后端的执行器。
   Icon Library 与正式胶囊控件共同迁移，使用同一套几何定义。
4. 按实际测量的编译和上传开销，增加常驻资源、批量实例、预热与有界任务合并。
   再扩展到面板外观、视图立方体和其余自绘内容。
5. 相关消费者和后端验收通过后，移除已迁移部分的自定义 ImDrawList 调用、临时剖分和专用 ImGui 绘图补丁。
   既有控件交互行为保持一致。

正确性验收至少覆盖：

- 12/16/24/32/128 px 图标，1x/1.5x/2x DPI，非整数位置。
- Rotate 小间隙、G3 圆角、多种透明度的部件重叠、嵌套裁剪与图层。
- 弹窗遮挡、滚动、镜像与非均匀变换、Unicode 文字。
- 目标尺寸变化、多窗口、资源销毁和预算耗尽。
- 完整场景图像及透明目标 alpha；仅看不透明背景截图无法发现全部合成错误。

性能分别测量冷、热编译时间，交互帧耗时的 p50/p95/p99，上传字节数，原生分配次数，draw call 数，
离屏图层面积，GPU 时间，队列延迟和缓存内存。
仅位置或颜色变化时，缓存命中路径不应重新编译或上传几何。

对比使用相同场景、同进程交替测量；根据基线制定数值预算，本文不宣称已经获得帧率提升。
扩展现有 Make 视觉验收与性能分析入口，并遵循[验证矩阵](../guides/testing.md#change-mapping)，
完成对应的原生与各后端检查。
